바이브코딩을 위한 데이터베이스 완전정복
— 단계별 셀프 강의 자료

AI와 함께 코딩(바이브코딩)할 때 가장 자주 막히는 지점이 "데이터를 어디에, 어떻게 저장할까"입니다. 이 자료는 돈 한 푼 안 들이고, 브라우저 안에서 바로 실습하면서 JSON → 브라우저 저장소 → 클라우드 DB 순서로 난이도를 높여가는 자기주도 학습용 강의입니다. 이 페이지 자체가 실습 도구입니다 — 스크롤하며 버튼을 눌러보세요.

전부 무료 기준 브라우저 실습 포함 JSON 예제 포함 2026년 8월 기준 스펙

시작하며

"바이브코딩"으로 Cursor, Claude, bolt.new, v0, Lovable 같은 도구를 쓰다 보면 프론트엔드는 술술 나오는데, "이 데이터를 저장했다가 나중에 다시 보여주려면 어떻게 하지?" 라는 질문에서 막히는 경우가 많습니다. 데이터베이스는 결국 "데이터를 어디에 남기고, 어떻게 다시 꺼내 쓸 것인가"에 대한 답일 뿐입니다.

📖 이 자료를 보는 법
본문에 이렇게 점선이 그어진 초록색 용어는 모두 하단 용어 사전으로 연결됩니다. 모르는 단어가 나오면 클릭 → 읽고 → 브라우저 뒤로가기로 돌아오세요. 용어 사전만 따로 훑어봐도 DB 대화가 훨씬 편해집니다.

이 강의는 아래 순서로 난이도를 올립니다.

  1. JSON이라는 데이터 형식부터 눈에 익힌다
  2. 서버 없이 브라우저 자체 저장소(localStorage, IndexedDB)로 데이터를 남겨본다
  3. 브라우저에서 진짜 SQL 데이터베이스를 돌려본다 (SQLite/Postgres WASM)
  4. JSON 파일 하나로 가짜 백엔드 API를 만들어 프론트엔드-서버 흐름을 익힌다
  5. 실제 서비스로 나갈 준비가 되면 무료 클라우드 DB(Supabase 등)로 갈아탄다
💡 이 순서로 배우는 이유
처음부터 클라우드 DB, 서버, 인증까지 한 번에 붙이면 무엇이 문제인지 구분이 안 됩니다. 브라우저 안에서 먼저 "데이터 저장·조회·삭제"라는 개념 자체를 체득한 다음, 같은 개념을 클라우드로 옮기면 훨씬 빠르게 이해됩니다.

데이터가 저장되는 위치 3가지

바이브코딩에서 "DB가 어렵다"고 느끼는 진짜 이유는, 데이터가 저장될 수 있는 장소가 여러 개인데 그 차이를 모른 채 섞어 쓰기 때문입니다. 크게 세 곳뿐입니다.

저장 위치대표 기술남는 범위언제 쓰나
① 메모리 (변수) JS 변수, React useState 새로고침하면 사라짐 화면에 잠깐 보여줄 값
② 브라우저 저장소 localStorage, IndexedDB 그 브라우저·그 기기에만 영구히 설정값, 오프라인 캐시, 로그인 전 임시 데이터
③ 서버(클라우드) DB Supabase, Firebase, Neon 모든 기기·모든 사용자가 공유 회원 데이터, 게시글, 결제 등 진짜 서비스 데이터

즉 "다른 컴퓨터에서 로그인해도 내 데이터가 보여야 한다" = ③번이 필요하다는 뜻입니다. 이 강의는 ① → ② → ③ 순서로 올라갑니다.

테이블 설계 맛보기 — 블로그를 예로

"회원이 글을 쓰고, 글에 댓글이 달린다"를 테이블로 옮기면 이렇게 됩니다. FK가 어떻게 관계를 만드는지 보세요.

SQL — 테이블 3개와 관계
-- ① 회원
create table users (
  id         bigint primary key generated always as identity,
  email      text unique not null,        -- unique: 중복 가입 방지
  name       text not null,
  created_at timestamptz default now()
);

-- ② 게시글 : 작성자(users.id)를 FK로 참조
create table posts (
  id         bigint primary key generated always as identity,
  title      text not null,
  body       text,
  author_id  bigint references users(id) on delete cascade,
  created_at timestamptz default now()
);

-- ③ 댓글 : 글과 작성자 양쪽을 참조
create table comments (
  id         bigint primary key generated always as identity,
  post_id    bigint references posts(id) on delete cascade,
  author_id  bigint references users(id) on delete cascade,
  body       text not null,
  created_at timestamptz default now()
);

-- 자주 조회하는 컬럼엔 인덱스를 걸어 속도를 확보
create index idx_posts_author on posts(author_id);
create index idx_comments_post on comments(post_id);
  • on delete cascade — 회원이 탈퇴하면 그 사람의 글·댓글도 함께 삭제. 이런 규칙을 참조 무결성이라고 합니다.
  • unique, not null 처럼 값에 거는 규칙을 제약조건(Constraint)이라 합니다.
  • 이렇게 데이터를 중복 없이 여러 테이블로 쪼개는 설계를 정규화라고 합니다.
  • 회원 1명이 글 여러 개를 쓰는 이런 형태를 1:N 관계라고 부릅니다 → 관계의 종류(1:1 · 1:N · N:M)

가장 많이 쓰는 SQL 5문장

SQL
-- 1. 조회: 특정 회원이 쓴 글을 최신순 10개
select id, title, created_at
from posts
where author_id = 3
order by created_at desc
limit 10;

-- 2. 생성
insert into posts (title, body, author_id) values ('첫 글', '내용', 3);

-- 3. 수정
update posts set title = '제목 변경' where id = 1;

-- 4. 삭제
delete from posts where id = 1;

-- 5. JOIN: 글과 작성자 이름을 한 번에 (관계형 DB의 핵심 기능)
select p.title, u.name as author
from posts p
join users u on u.id = p.author_id
order by p.created_at desc;

JOIN은 관계형 DB에서만 쓸 수 있는 기능으로, NoSQL에서는 보통 데이터를 미리 합쳐서 저장하거나(비정규화) 여러 번 조회해야 합니다. 이것이 두 방식의 가장 큰 실무적 차이입니다.

⚠️ 바이브코딩할 때 흔한 오해
"localStorage에 저장하면 DB 필요 없는 거 아냐?" — 아닙니다. localStorage는 그 브라우저, 그 기기에만 남습니다. 다른 기기에서 로그인해도 데이터가 안 보이는 이유가 이것입니다. 여러 기기·여러 사용자 간에 데이터를 공유하려면 결국 서버 어딘가에 있는 DB가 필요합니다. (아래 2·3단계에서 직접 체감해 보세요.)

1 JSON으로 데이터 다루기

난이도 ★☆☆☆☆ · 소요시간 10분 · 모든 DB·API가 결국 이 형식으로 대화합니다

JSON(JavaScript Object Notation)은 데이터를 { 키: 값 } 형태로 표현하는 텍스트 형식입니다. 브라우저 저장소, REST API, 클라우드 DB 응답까지 전부 JSON을 주고받습니다.

JSON 예제
{
  "id": 1,
  "name": "김바이브",
  "email": "vibe@example.com",
  "isActive": true,
  "tags": ["frontend", "ai-coding"],
  "profile": {
    "level": "beginner",
    "joinedAt": "2026-08-03"
  }
}

규칙 6가지

  • 키(key)는 반드시 큰따옴표(")로 감쌉니다. 작은따옴표(')는 오류입니다.
  • 값으로 쓸 수 있는 타입은 딱 6가지: 문자열, 숫자, true/false, null, 배열([]), 객체({}). 함수·날짜 객체·undefined는 넣을 수 없습니다.
  • 마지막 항목 뒤에 쉼표를 붙이면 오류입니다 (trailing comma 금지).
  • 주석(//, /* */)을 쓸 수 없습니다.
  • 날짜는 타입이 없으므로 ISO 8601 문자열("2026-08-03T09:00:00Z")로 저장하는 것이 국제 관례입니다.
  • JS 객체와 거의 똑같이 생겼지만, JSON은 "텍스트(문자열)"이고 JS 객체는 "메모리 상의 값"이라는 결정적 차이가 있습니다.

직렬화 / 역직렬화 — 이 두 함수가 전부입니다

객체를 텍스트로 바꾸는 것을 직렬화(Serialize), 텍스트를 다시 객체로 되돌리는 것을 역직렬화(Parse)라고 합니다. 2단계 localStorage부터 7단계 클라우드 DB까지 계속 등장합니다.

JavaScript
const user = { id: 1, name: "김바이브", joinedAt: new Date() };

// 직렬화: 객체 → JSON 문자열
const text = JSON.stringify(user);
// '{"id":1,"name":"김바이브","joinedAt":"2026-08-03T09:00:00.000Z"}'
//  ↑ Date 객체가 자동으로 문자열로 바뀐 것에 주목

// 역직렬화: JSON 문자열 → 객체
const back = JSON.parse(text);
typeof back.joinedAt;  // "string" ← Date가 아니라 문자열로 돌아옴!
new Date(back.joinedAt); // 필요하면 직접 Date로 복원해야 함

// 보기 좋게 들여쓰기해서 출력 (두 번째 인자 null, 세 번째 인자 = 공백 수)
console.log(JSON.stringify(user, null, 2));
⚠️ 초보자가 100% 겪는 함정
  • Date가 문자열이 된다 — JSON.parse 후 .getFullYear()를 부르면 에러. 직접 new Date(...)로 복원해야 합니다.
  • [object Object]가 저장됨 — JSON.stringify를 빼먹고 객체를 그대로 localStorage.setItem에 넣은 경우입니다.
  • undefined는 조용히 사라진다 — {a:1, b:undefined}는 {"a":1}이 됩니다.
  • 순환 참조는 에러 — 객체가 자기 자신을 참조하면 Converting circular structure to JSON 오류가 납니다.

JSON과 DB의 관계

같은 데이터가 저장 위치에 따라 어떻게 표현되는지 비교해 보세요. 형태만 다를 뿐 내용은 같습니다.

위치표현 방식
JSON 파일 / API 응답{"id":1,"name":"김바이브"}
관계형 DB (Postgres)users 테이블의 한 행: id=1, name='김바이브'
NoSQL (Firestore)users 컬렉션의 문서 하나 — JSON과 거의 같은 모양 그대로 저장

Postgres에는 jsonb라는 타입도 있어서, 구조가 자주 바뀌는 데이터는 컬럼 하나에 JSON 통째로 넣고 나머지는 일반 컬럼으로 쓰는 하이브리드 설계도 자주 씁니다.

2 브라우저 저장소 — localStorage / sessionStorage

난이도 ★★☆☆☆ · 서버 없이 브라우저에만 데이터를 남기는 가장 쉬운 방법

localStorage는 브라우저(정확히는 출처/origin)마다 주어지는 키-값 저장 공간입니다. 용량은 보통 도메인당 5~10MB, 브라우저를 닫아도 데이터가 남습니다. sessionStorage는 문법이 동일하지만 탭을 닫으면 사라집니다.

JavaScript
// 저장 — 값은 반드시 문자열이어야 하므로 객체는 JSON.stringify로 변환
localStorage.setItem("vibe_notes", JSON.stringify([{ id: 1, text: "첫 메모" }]));

// 조회 — 꺼낼 땐 JSON.parse로 다시 객체로 변환
const notes = JSON.parse(localStorage.getItem("vibe_notes") || "[]");

// 삭제
localStorage.removeItem("vibe_notes");
localStorage.clear(); // 전체 삭제

    실무에서 쓰는 안전한 래퍼 함수

    사용자가 시크릿 모드를 쓰거나 용량이 꽉 차면 setItem이 예외를 던집니다. 실무에서는 보통 이렇게 감싸 둡니다.

    JavaScript
    const storage = {
  get(key, fallback = null) {
    try {
      const raw = localStorage.getItem(key);
      return raw === null ? fallback : JSON.parse(raw);
    } catch {
      return fallback;               // 깨진 JSON이 들어있어도 앱이 죽지 않게
    }
  },
  set(key, value) {
    try {
      localStorage.setItem(key, JSON.stringify(value));
      return true;
    } catch (e) {
      console.warn("저장 실패(용량 초과 또는 시크릿 모드):", e);
      return false;
    }
  },
  remove(key) { localStorage.removeItem(key); }
};

    ⚠️ 한계와 금지사항
    • 문자열만 저장 가능 — 매번 JSON.stringify/parse를 직접 해야 합니다.
    • 검색·정렬·조건 조회 불가 — 전체를 꺼내 JS로 필터링해야 하므로 데이터가 많아지면 느려집니다.
    • 동기(synchronous) 동작 — 큰 데이터를 읽고 쓰는 동안 화면이 멈춥니다. 그래서 3단계 IndexedDB가 필요합니다.
    • 기기 간 공유 불가 — 휴대폰에서 저장한 값은 PC에서 안 보입니다.
    • 비밀번호·토큰·개인정보 저장 금지 — 개발자도구 Application 탭에서 누구나 그대로 읽을 수 있고, XSS 공격에 그대로 노출됩니다.

    3 IndexedDB — 브라우저 내장 진짜 데이터베이스

    난이도 ★★★☆☆ · localStorage보다 훨씬 큰 용량, 진짜 "여러 건 데이터 관리" 체험

    IndexedDB는 브라우저에 내장된 NoSQL(객체 저장소) 데이터베이스입니다. 용량은 보통 기기 저장공간의 일정 비율까지 (수백 MB~GB 단위) 사용 가능하고, 인덱스를 걸어 빠르게 검색할 수 있습니다. 오프라인 앱, PWA에서 많이 씁니다. 다만 API가 다소 번거로워서 실무에서는 Dexie.js 같은 래퍼 라이브러리를 함께 씁니다.

    JavaScript — 순수 IndexedDB API
    const req = indexedDB.open("vibeDB", 1);

req.onupgradeneeded = (e) => {
  const db = e.target.result;
  // notes 라는 객체 저장소(테이블과 유사) 생성, id를 자동 증가 키로 사용
  db.createObjectStore("notes", { keyPath: "id", autoIncrement: true });
};

req.onsuccess = (e) => {
  const db = e.target.result;
  const tx = db.transaction("notes", "readwrite");
  tx.objectStore("notes").add({ text: "첫 메모", createdAt: Date.now() });
};

const db = new Dexie("vibeDB");

      IndexedDB 용어 4개만 알면 됩니다

      용어관계형 DB로 치면설명
      Object Store 테이블 데이터를 담는 그릇. createObjectStore("notes", ...)로 생성
      keyPath / autoIncrement Primary Key 각 데이터를 구분하는 키. autoIncrement: true면 1,2,3... 자동 부여

      Cursor SELECT 결과 순회 저장된 데이터를 한 건씩 훑으며 읽는 도구

      JavaScript — 인덱스를 걸고 조건 검색하기
      const req = indexedDB.open("vibeDB", 2);   // ← 버전을 2로 올림

req.onupgradeneeded = (e) => {
  const db = e.target.result;
  const store = e.target.transaction.objectStore("notes");
  // createdAt 으로 빠르게 정렬·검색하기 위한 인덱스 추가
  if (!store.indexNames.contains("byCreatedAt")) {
    store.createIndex("byCreatedAt", "createdAt");
  }
};

// 특정 기간의 데이터만 읽기 (IDBKeyRange = SQL의 WHERE ... BETWEEN 과 비슷)
function findRecent(db, sinceTs) {
  return new Promise((resolve) => {
    const results = [];
    const idx = db.transaction("notes").objectStore("notes").index("byCreatedAt");
    idx.openCursor(IDBKeyRange.lowerBound(sinceTs)).onsuccess = (e) => {
      const c = e.target.result;
      if (c) { results.push(c.value); c.continue(); } else resolve(results);
    };
  });
}

      OPFS — 더 최신의 브라우저 파일 저장소

      최근에는 OPFS(Origin Private File System)라는 방식도 지원됩니다. 브라우저가 사이트별로 제공하는 비공개 파일 시스템으로, IndexedDB보다 읽고 쓰는 속도가 훨씬 빠릅니다. 4단계에서 소개할 브라우저용 SQLite/Postgres가 데이터를 실제 파일처럼 저장할 때 이 OPFS를 사용합니다. 직접 다룰 일은 많지 않지만, "왜 브라우저에서 DB 파일이 유지되지?"의 답이 바로 이것입니다.

      💡 언제 IndexedDB를 쓸까
      오프라인에서도 동작해야 하는 앱, 대용량 캐시, 파일/이미지 Blob 저장, 서버 동기화 전 임시 버퍼, PWA 등에 적합합니다. "로그인한 사용자의 데이터를 여러 기기에서 공유"해야 한다면 결국 6~7단계의 클라우드 DB가 필요합니다.
      ⚠️ 브라우저 저장소는 영구 보장이 아닙니다
      저장 공간이 부족하거나 사용자가 브라우저 데이터를 삭제하면 IndexedDB 내용도 함께 사라질 수 있습니다. (Eviction) 잃어버리면 안 되는 데이터는 반드시 서버 DB에도 저장하세요.

      4 브라우저에서 진짜 SQL 써보기

      난이도 ★★★☆☆ · SELECT / INSERT 문법에 익숙해지는 단계

      🔐 SQL 인젝션 — 반드시 알아야 할 보안 개념

      SQL 문자열을 직접 이어붙이면 공격자가 임의의 SQL을 실행할 수 있습니다. 이를 SQL 인젝션이라 하고, 반드시 파라미터 바인딩(? 또는 $1)을 써야 합니다.

      // ❌ 절대 금지 — userInput이 "'; drop table notes; --" 이면 테이블이 삭제됨
db.run("SELECT * FROM notes WHERE text = '" + userInput + "'");

// ✅ 올바른 방법 — 값이 SQL 문법이 아닌 '데이터'로만 취급됨
db.run("SELECT * FROM notes WHERE text = ?", [userInput]);      // SQLite
await db.query("SELECT * FROM notes WHERE text = $1", [userInput]); // Postgres
      💡 왜 이 단계가 중요한가
      7단계에서 만날 Supabase, Neon, Turso는 모두 SQL(Postgres 또는 SQLite 문법)을 씁니다. 여기서 CREATE TABLE, SELECT ... WHERE, INSERT INTO 정도만 손에 익혀두면 클라우드 DB로 넘어갈 때 문법 때문에 막히지 않습니다. 연습은 SQLBolt(인터랙티브, 무료)와 PGlite 온라인 REPL(설치 없이 브라우저에서 Postgres 실행)을 추천합니다.

      생성 (Create)POST/postsinsert into posts ...
      전체 수정 (Update)PUT/posts/1update posts set ... where id=1
      부분 수정 (Update)PATCH/posts/1update posts set title=... where id=1

      • 실시간 채팅·좋아요처럼 즉각 반영되는 앱, NoSQL 선호 → Firebase

      BaaS vs 순수 DB — 무엇을 고르고 있는 건가

      Supabase와 Firebase는 BaaS(Backend as a Service)로, DB뿐 아니라 회원가입/로그인(Auth), 파일 스토리지, 서버 함수까지 한 묶음으로 제공합니다. Neon과 Turso는 DB만 제공하므로 인증은 직접 붙여야 합니다. 혼자 빠르게 서비스를 만들려면 BaaS가, 이미 백엔드 구조가 있다면 순수 DB가 유리합니다.

      3) RLS(행 단위 보안) 제대로 이해하기

      RLS(Row Level Security)는 "이 사용자가 이 행을 봐도 되는가"를 DB 자체가 판단하게 하는 기능입니다. Supabase는 anon key가 브라우저에 그대로 노출되는 구조이므로, RLS가 사실상 유일한 방어선입니다. RLS를 켜지 않은 테이블 = 인터넷 전체에 공개된 테이블이라고 생각하세요.

      SQL — 실전 RLS 정책 4종 세트
      -- 테이블에 소유자 컬럼을 두는 것이 출발점
alter table notes add column user_id uuid default auth.uid() references auth.users(id);

alter table notes enable row level security;

-- 조회: 자기 것만
create policy "select_own" on notes
  for select using (auth.uid() = user_id);

-- 생성: 자기 id로만 삽입 가능 (남의 이름으로 쓰기 방지)
create policy "insert_own" on notes
  for insert with check (auth.uid() = user_id);

-- 수정: 자기 것만
create policy "update_own" on notes
  for update using (auth.uid() = user_id);

-- 삭제: 자기 것만
create policy "delete_own" on notes
  for delete using (auth.uid() = user_id);

      using은 "이미 있는 행 중 무엇을 볼/고칠 수 있는가", with check는 "새로 들어오는 값이 조건에 맞는가"를 검사합니다. 이 둘의 차이가 RLS에서 가장 헷갈리는 지점입니다.

      ① 기본 개념

      데이터베이스 Database, DB

      데이터를 구조를 갖춰 저장하고, 원하는 조건으로 다시 꺼낼 수 있게 관리하는 시스템. 단순한 파일 저장과의 차이는 "검색·정렬·동시 접근·정합성 보장"이 된다는 점입니다.
      엑셀 파일도 데이터를 담지만, 100명이 동시에 고칠 때 순서를 보장해 주지는 못합니다. 그걸 해 주는 게 DB입니다.

      CRUD Create · Read · Update · Delete

      데이터를 다루는 네 가지 기본 동작. 어떤 DB든, 어떤 API든 결국 이 네 가지의 조합입니다. "CRUD를 붙인다"는 말은 "추가/조회/수정/삭제 기능을 만든다"는 뜻입니다.
      SQL: INSERT / SELECT / UPDATE / DELETE  ·  REST: POST / GET / PUT·PATCH / DELETE  → 5단계에서 대응표 확인

      테이블 · 컬렉션 Table · Collection

      같은 종류의 데이터를 모아두는 단위. 관계형 DB에서는 테이블, NoSQL에서는 컬렉션이라 부릅니다. 엑셀의 "시트 한 장"에 해당합니다.
      예: users(회원), posts(게시글), orders(주문) — 보통 영어 소문자 복수형으로 이름 짓습니다.

      행(Row) · 문서(Document) · 레코드 Row · Document · Record

      데이터 한 건. 사용자 한 명, 게시글 하나가 각각 하나의 행입니다. 엑셀의 가로 한 줄.
      users 테이블에 회원이 300명이면 → 행이 300개.

      열(Column) · 필드(Field) Column · Field

      데이터가 가지는 속성 하나. 각 열에는 타입(문자/숫자/날짜/불리언 등)이 정해져 있습니다.
      자주 쓰는 타입: text(문자), int·bigint(정수), boolean(참/거짓), timestamptz(시간대 포함 시각), uuid(고유 식별자), jsonb(JSON 통째로)

      스키마 Schema

      어떤 테이블에 어떤 컬럼이 어떤 타입으로 들어가는지 정의한 설계도. 관계형 DB는 스키마를 미리 정해야 하고(schema-on-write), NoSQL은 나중에 자유롭게 바꿀 수 있습니다(schema-less).
      스키마를 먼저 종이에 그려보고 AI에게 요청하면, 나중에 갈아엎는 일이 크게 줄어듭니다.

      마이그레이션 Migration

      이미 데이터가 들어있는 상태에서 스키마를 바꾸는 작업(컬럼 추가, 타입 변경 등)과 그 변경 이력 파일. "버전 관리되는 DB 구조 변경"이라고 생각하면 됩니다.
      IndexedDB에서는 open(name, 2)처럼 버전을 올리면 onupgradeneeded가 실행되는 것이 마이그레이션입니다. → 3단계 참고

      ORM Object-Relational Mapping

      SQL을 직접 쓰지 않고 코드(객체)로 DB를 다루게 해 주는 도구. 타입 자동완성이 되어 실수가 줄지만, 내부에서 어떤 SQL이 나가는지 모르면 성능 문제를 놓치기 쉽습니다.
      대표 도구: Prisma, Drizzle (JS/TS) · SQLAlchemy (Python)

      NoSQL Not Only SQL

      테이블·행 구조를 쓰지 않는 DB의 총칭. 문서형(Firestore, MongoDB), 키-값형(Redis), 그래프형 등이 있습니다. 스키마가 자유롭고 확장이 쉬운 대신, JOIN이 없고 데이터 정합성은 개발자가 직접 챙겨야 합니다.
      "댓글 수"를 알고 싶을 때 SQL은 count(*) 한 줄이지만, NoSQL은 보통 문서 안에 commentCount 필드를 두고 직접 갱신합니다.

      직렬화 Serialize

      메모리 상의 객체를 저장·전송할 수 있는 문자열로 바꾸는 것. JS에서는 JSON.stringify().
      localStorage, 네트워크 전송, 파일 저장 — 데이터가 프로그램 밖으로 나갈 때는 반드시 직렬화가 필요합니다. → 1단계

      역직렬화 · 파싱 Deserialize · Parse

      문자열을 다시 프로그램이 다룰 수 있는 객체로 되돌리는 것. JS에서는 JSON.parse().
      Date 객체는 파싱 후 문자열로 돌아온다는 점에 주의. new Date(obj.createdAt)로 직접 복원해야 합니다.
      ② SQL · 관계형 DB

      SQL Structured Query Language

      관계형 DB에 명령을 내리는 표준 언어. 프로그래밍 언어라기보다는 "원하는 결과를 서술하는 언어"에 가깝습니다. 읽는 순서는 FROM → WHERE → GROUP BY → SELECT → ORDER BY → LIMIT.
      → 무료 연습: SQLBolt · PGlite 온라인 REPL

      PostgreSQL 포스트그레스, 줄여서 Postgres

      가장 널리 쓰이는 오픈소스 관계형 DB. 기능이 풍부하고(JSON 타입, 전문검색, 벡터검색 확장 등) 무료입니다. Supabase·Neon이 모두 Postgres 기반이라, 하나 익혀두면 서비스를 옮겨도 그대로 통합니다.
      → PostgreSQL Tutorial

      SQLite 에스큐엘라이트

      서버가 없는 파일 하나짜리 DB. 설치도 서버 프로세스도 필요 없어 모바일 앱·데스크톱 앱·브라우저에 내장됩니다. 세상에서 가장 많이 배포된 DB로 알려져 있습니다.
      브라우저에서 돌리는 방법 → 4단계 (sql.js, wa-sqlite), 클라우드 버전 → Turso

      기본키 Primary Key, PK

      각 행을 유일하게 구분하는 값. 중복될 수 없고 비어 있을 수 없습니다. 보통 id 컬럼.
      자동 증가 정수(1,2,3…)는 읽기 편하지만 순서가 추측 가능하고, UUID(a3f1...)는 추측이 어렵고 여러 서버에서 동시에 만들어도 겹치지 않습니다. 공개 URL에 노출된다면 UUID를 권장.

      외래키 Foreign Key, FK

      다른 테이블의 기본키를 가리켜 관계를 만드는 컬럼. 관계형 DB가 "관계형"인 이유입니다.
      posts.author_id → users.id = "이 글은 3번 회원이 썼다". on delete cascade를 붙이면 회원 삭제 시 글도 함께 삭제됩니다.

      관계의 종류 1:1 · 1:N · N:M

      테이블끼리 맺는 관계의 형태입니다.
      1:1 회원 ↔ 프로필 (한 명당 하나)
      1:N 회원 → 게시글 (한 명이 여러 글) — 가장 흔함. "N쪽"에 FK를 둡니다
      N:M 게시글 ↔ 태그 (글도 태그 여러 개, 태그도 글 여러 개) — 중간 테이블(post_tags)이 필요합니다

      조인 JOIN

      두 개 이상의 테이블을 연결해서 한 번에 조회하는 기능. 관계형 DB의 가장 큰 무기입니다.
      INNER JOIN 양쪽 모두 있는 것만 · LEFT JOIN 왼쪽은 다 보여주고 오른쪽은 없으면 null. "글은 다 보여주되 작성자가 탈퇴했을 수도 있다" → LEFT JOIN

      인덱스 Index

      특정 컬럼으로 빠르게 찾기 위한 색인. 책 뒤의 '찾아보기'와 같습니다. 조회는 극적으로 빨라지지만, 쓰기가 조금 느려지고 저장 공간을 더 씁니다.
      create index idx_posts_author on posts(author_id);
      거는 기준: where·join·order by에 자주 등장하는 컬럼. 모든 컬럼에 다 걸면 오히려 손해입니다.

      풀 스캔 Full Table Scan

      인덱스가 없어서 DB가 테이블 전체를 처음부터 끝까지 훑는 상황. 데이터가 많아질수록 급격히 느려지고, 클라우드 DB에서는 "읽은 행 수" 과금이 폭증하는 원인이 됩니다.
      쿼리 앞에 explain analyze를 붙이면 풀 스캔인지 인덱스를 탔는지 확인할 수 있습니다.

      제약조건 Constraint

      컬럼 값에 거는 규칙. 잘못된 데이터가 애초에 들어오지 못하게 DB 차원에서 막습니다.
      not null(빈 값 금지) · unique(중복 금지) · default(기본값) · check (price > 0)(조건 검사)

      참조 무결성 Referential Integrity

      FK가 가리키는 대상이 실제로 존재함을 DB가 보장하는 것. 없는 회원 번호로 글을 쓰는 것 자체가 막힙니다. NoSQL에는 이 기능이 없어서 "작성자가 사라진 유령 게시글"이 생기기 쉽습니다.
      on delete cascade(함께 삭제) · on delete set null(참조만 비움) · 기본값은 삭제 자체를 거부

      정규화 · 비정규화 Normalization · Denormalization

      정규화는 중복을 없애려고 데이터를 여러 테이블로 쪼개는 설계, 비정규화는 조회 속도를 위해 일부러 중복 저장하는 설계입니다.
      회원 이름을 users에만 두면(정규화) 이름 변경이 한 번에 반영되지만 매번 JOIN해야 하고, posts에도 복사해 두면(비정규화) 조회는 빠르지만 이름이 바뀔 때 전부 고쳐야 합니다. NoSQL은 보통 비정규화를 씁니다.

      트랜잭션 Transaction

      여러 작업을 "전부 성공 아니면 전부 취소"로 묶는 단위. 중간에 실패하면 앞의 작업까지 되돌립니다.
      A 계좌에서 빼고 B 계좌에 넣는 도중 오류가 나면, 돈이 증발하지 않도록 전체를 되돌립니다. 이 성질을 ACID(원자성·일관성·격리성·지속성)라고 부릅니다.

      롤백 · 커밋 Rollback · Commit

      커밋은 트랜잭션의 변경을 확정하는 것, 롤백은 되돌리는 것입니다.
      begin; ... commit; / 중간에 문제가 있으면 rollback;

      집계 함수 Aggregate Function

      여러 행을 하나의 값으로 요약하는 함수. GROUP BY와 함께 자주 씁니다.
      count(*)(개수) · sum()(합) · avg()(평균) · max()/min()
      select author_id, count(*) from posts group by author_id; → 작성자별 글 개수

      페이지네이션 Pagination

      데이터를 한 번에 다 가져오지 않고 페이지 단위로 나눠 가져오는 기법. 성능과 무료 티어 사용량을 지키는 가장 기본적인 습관입니다.
      limit 10 offset 20 (3페이지) · Supabase: .range(20, 29)
      데이터가 아주 많으면 offset 대신 "마지막 id 이후"를 조건으로 쓰는 커서 방식이 더 빠릅니다.
      ③ 브라우저 저장소

      localStorage 로컬 스토리지

      브라우저에 문자열 키-값을 영구 저장하는 가장 간단한 방법. 약 5~10MB, 동기 동작. 같은 출처에서만 접근 가능하고 다른 기기와는 공유되지 않습니다.
      localStorage.setItem("k", JSON.stringify(obj)) → 2단계 실습 · MDN 문서

      IndexedDB 인덱스드 디비

      브라우저에 내장된 비동기 NoSQL 데이터베이스. 수백 MB~GB 단위 저장, 인덱스 검색, 트랜잭션을 지원합니다. API가 번거로워 보통 Dexie.js 같은 래퍼와 함께 씁니다.
      → 3단계 실습 · MDN 문서

      오브젝트 스토어 Object Store

      IndexedDB에서 데이터를 담는 그릇. 관계형 DB의 테이블에 해당합니다.
      db.createObjectStore("notes", { keyPath: "id", autoIncrement: true })

      keyPath · autoIncrement

      IndexedDB에서 각 데이터를 구분하는 키를 정하는 방법. keyPath는 어떤 속성을 키로 쓸지, autoIncrement는 키를 자동으로 1,2,3… 부여할지 결정합니다. 관계형 DB의 기본키에 해당합니다.

      커서 Cursor

      저장된 데이터를 한 건씩 순회하며 읽는 도구. IndexedDB에는 "전부 가져오기" 대신 커서로 훑는 방식이 기본입니다.
      store.openCursor().onsuccess = e => { const c = e.target.result; if(c){ ...; c.continue(); } }

      OPFS Origin Private File System

      브라우저가 사이트마다 제공하는 비공개 파일 시스템. IndexedDB보다 읽기/쓰기가 훨씬 빨라, 브라우저용 SQLite·Postgres가 DB 파일을 저장하는 데 사용합니다.
      사용자의 실제 폴더가 아니라 브라우저 내부의 격리된 공간이며, 브라우저 데이터 삭제 시 함께 지워집니다.

      WebAssembly WASM

      C·C++·Rust로 만든 프로그램을 브라우저에서 실행할 수 있게 컴파일한 형식. 덕분에 SQLite·PostgreSQL 같은 네이티브 프로그램이 웹페이지 안에서 그대로 돌아갑니다.
      → 4단계 (sql.js, PGlite)

      Blob Binary Large Object

      이미지·오디오·파일 같은 바이너리 데이터 덩어리. localStorage에는 못 넣지만 IndexedDB에는 그대로 저장할 수 있습니다.
      서버 DB에는 파일 자체가 아니라 스토리지에 올린 뒤 그 URL만 저장하는 것이 정석입니다.

      Eviction 저장소 자동 삭제

      기기 저장 공간이 부족하거나 오래 방문하지 않으면 브라우저가 저장 데이터를 임의로 지울 수 있는 정책. 브라우저 저장소는 "영구 보관"이 보장되지 않습니다.
      navigator.storage.persist()로 영구 저장을 요청할 수 있지만 브라우저가 거절할 수도 있습니다.

      PWA Progressive Web App

      웹사이트를 앱처럼 설치하고 오프라인에서도 쓰게 만드는 기술 묶음. 오프라인 데이터 저장에 IndexedDB를 사용합니다.

      출처 Origin

      프로토콜 + 도메인 + 포트의 조합. 브라우저 저장소와 보안 정책의 경계 단위입니다. 하나라도 다르면 완전히 별개의 공간으로 취급됩니다.
      http://localhost:3000과 http://localhost:5173은 다른 출처입니다. 개발 중 "저장한 데이터가 안 보여요"의 흔한 원인.

      쿠키 Cookie

      약 4KB의 작은 데이터로, 모든 요청에 자동으로 서버에 함께 전송되는 것이 특징입니다. 그래서 로그인 세션 유지에 주로 쓰입니다.
      HttpOnly 옵션을 주면 JS가 읽을 수 없어 XSS에 강해집니다. 토큰은 localStorage보다 HttpOnly 쿠키가 더 안전하다고 보는 이유입니다.
      ④ API · 네트워크

      API Application Programming Interface

      프로그램끼리 대화하는 약속된 창구. "이 주소로 이런 형식으로 요청하면, 이런 형식으로 답을 준다"는 규격입니다.
      식당의 메뉴판에 비유됩니다. 주방(서버·DB)이 어떻게 생겼는지 몰라도 메뉴판(API)대로 주문하면 음식이 나옵니다.

      REST · RESTful API

      "URL은 자원을 가리키고, HTTP 메서드가 동작을 나타낸다"는 API 설계 관례. 현재 가장 널리 쓰입니다.
      GET /posts/1 = 1번 글 조회. URL에 동사를 넣지 않는 것(/getPost ✕)이 핵심 원칙입니다. → 5단계 대응표

      HTTP 메서드 GET · POST · PUT · PATCH · DELETE

      요청의 의도를 나타내는 표식. CRUD와 1:1로 대응합니다.
      GET은 데이터를 바꾸지 않아야 하고(캐시될 수 있음), PUT은 전체 교체, PATCH는 일부만 수정입니다.

      엔드포인트 Endpoint

      API의 각 기능에 해당하는 개별 URL 주소.
      https://api.example.com/v1/posts ← 이 주소 하나가 하나의 엔드포인트

      상태 코드 HTTP Status Code

      요청 결과를 나타내는 세 자리 숫자. 앞자리로 성격을 알 수 있습니다: 2xx 성공, 4xx 요청한 쪽 잘못, 5xx 서버 잘못.
      4xx가 뜨면 내 코드를, 5xx가 뜨면 서버/DB 설정을 먼저 의심하세요. → 5단계 표

      CORS Cross-Origin Resource Sharing

      다른 출처의 서버에 요청할 때 브라우저가 적용하는 보안 정책. 서버가 "허용한다"는 응답 헤더를 보내지 않으면 브라우저가 응답을 차단합니다.
      프론트엔드 코드로는 고칠 수 없습니다. 서버 쪽에 Access-Control-Allow-Origin 설정을 추가해야 합니다.

      비동기 Asynchronous, async/await

      결과를 기다리는 동안 다른 일을 계속 할 수 있게 하는 방식. DB 조회·네트워크 요청은 시간이 걸리므로 거의 전부 비동기입니다.
      await를 빼먹으면 데이터 대신 Promise {<pending>}이 찍힙니다. "데이터가 undefined로 나와요"의 1순위 원인입니다.

      실시간 구독 Realtime · Subscription

      DB 데이터가 바뀌면 서버가 먼저 알려줘서 화면이 자동 갱신되는 기능. 내부적으로 WebSocket을 사용합니다.
      채팅, 좋아요 수, 협업 편집 등에 사용. → 7단계 예제
      ⑤ 클라우드 · 요금 용어

      BaaS Backend as a Service

      DB·인증·파일 저장·서버 함수를 한 묶음으로 제공하는 서비스. 백엔드 서버를 직접 만들지 않아도 프론트엔드 코드만으로 서비스를 완성할 수 있습니다.
      대표: Supabase(Postgres 기반), Firebase(NoSQL 기반) — 바이브코딩과 가장 궁합이 좋은 형태

      서버리스 Serverless

      서버가 없다는 뜻이 아니라, 서버 관리를 내가 하지 않고 쓴 만큼만 과금되는 방식. 요청이 없으면 자동으로 잠들고, 트래픽이 늘면 알아서 확장됩니다.
      잠든 상태에서 깨어날 때 지연이 생기는 것이 콜드 스타트입니다.

      콜드 스타트 Cold Start

      잠들어 있던 서버·DB가 첫 요청을 받고 깨어나는 데 걸리는 시간(보통 수백 ms~수 초). 무료 티어에서 "가끔 첫 로딩이 유난히 느린" 이유입니다.

      Egress 아웃바운드 전송량

      서버에서 바깥으로 나간 데이터의 총량. 무료 티어에서 가장 먼저 소진되기 쉬운 항목입니다.
      필요한 컬럼만 select하고, 이미지는 DB가 아닌 스토리지/CDN에 두면 크게 절약됩니다.

      MAU Monthly Active Users, 월간 활성 사용자

      한 달 동안 실제로 활동한 고유 사용자 수. 인증 기능 요금의 기준으로 자주 쓰입니다.

      CU-hour Compute Unit Hour

      DB 서버가 깨어 있던 시간 × 성능 단위. Neon 같은 서버리스 Postgres의 과금 기준입니다. 자동 절전 덕분에 개발용으로는 무료 한도 안에서 충분한 경우가 많습니다.

      Rows read 읽은 행 수

      쿼리가 실제로 훑고 지나간 행의 개수. 반환된 결과 개수가 아니라 스캔한 개수라는 점이 중요합니다. Turso 등의 과금 기준입니다.
      결과가 1건이어도 인덱스가 없으면 10만 행을 훑었을 수 있습니다 → 인덱스가 요금을 줄여줍니다.

      커넥션 풀 Connection Pooling

      DB 연결을 매번 새로 만들지 않고 미리 만들어 둔 연결을 돌려쓰는 기법. 서버리스 환경에서는 연결 수가 폭증하기 쉬워 필수입니다.
      Supabase·Neon은 별도의 pooler 접속 주소를 제공합니다. Vercel 등에 배포할 때 일반 주소 대신 이 주소를 쓰세요.
      ⑥ 보안

      인증 vs 인가 Authentication vs Authorization

      인증(Authn)은 "당신이 누구인지" 확인하는 것(로그인), 인가(Authz)는 "이 데이터를 다룰 권한이 있는지" 판단하는 것입니다. 둘은 다릅니다.
      Supabase에서 인증은 supabase.auth, 인가는 RLS 정책이 담당합니다.

      RLS Row Level Security, 행 단위 보안

      "이 사용자가 이 행을 조회·수정해도 되는가"를 DB 자체가 판단하게 하는 Postgres 기능. 클라이언트에서 직접 DB에 접근하는 Supabase 구조에서는 사실상 유일한 방어선입니다.
      RLS를 끈 테이블 = 인터넷에 공개된 테이블. AI가 만든 코드는 RLS를 빼먹기 쉬우니 반드시 직접 확인하세요. → 7단계 예제

      anon key vs service_role key

      anon key는 브라우저에 노출되어도 되는 공개 키로, RLS 정책의 통제를 받습니다. service_role key는 RLS를 무시하는 마스터 키로, 서버에서만 사용해야 합니다.
      service_role key를 프론트엔드나 GitHub에 올리는 것은 DB 비밀번호를 공개하는 것과 같습니다.

      환경변수 Environment Variable, .env

      API 키처럼 코드에 직접 쓰면 안 되는 값을 별도 파일로 분리해 두는 방식. .env 파일은 반드시 .gitignore에 추가합니다.
      VITE_·NEXT_PUBLIC_으로 시작하는 변수는 브라우저에 그대로 노출됩니다. 비밀 키에는 이 접두사를 절대 붙이지 마세요.

      SQL 인젝션 SQL Injection

      사용자 입력을 SQL 문자열에 그대로 이어붙였을 때, 공격자가 임의의 SQL을 실행시키는 공격. 가장 오래되고 여전히 흔한 취약점입니다.
      방어법은 하나뿐 — 파라미터 바인딩을 쓰는 것. → 4단계 예제

      파라미터 바인딩 Prepared Statement

      값을 SQL 문자열에 섞지 않고 ?나 $1 자리표시자로 따로 전달하는 방식. 값이 SQL 문법이 아닌 '데이터'로만 취급되어 인젝션이 원천 차단됩니다.
      db.query("select * from users where email = $1", [email])

      XSS Cross-Site Scripting

      공격자가 심어둔 스크립트가 다른 사용자의 브라우저에서 실행되는 공격. 성공하면 localStorage에 저장된 토큰이 그대로 탈취됩니다.
      사용자 입력을 innerHTML로 그리지 말고 textContent를 쓰거나, React처럼 자동 이스케이프되는 방식을 사용하세요.

      백업 Backup

      데이터의 복사본을 별도로 보관하는 것. 대부분의 무료 티어에는 자동 백업이 없습니다.
      중요한 프로젝트라면 주기적으로 데이터를 내려받아 두세요. Postgres는 pg_dump, Supabase는 대시보드에서 CSV 내보내기를 제공합니다.

      바이브코딩 중 자주 하는 실수 10가지

      AI가 만들어 준 코드에서 특히 자주 발견되는 문제들입니다. 배포 전에 한 번씩 확인하세요.

      #증상 / 실수왜 문제인가해결
      1RLS를 켜지 않고 배포 anon key만 있으면 누구나 전체 테이블을 읽고 삭제 가능 테이블마다 RLS 활성화 + 정책 4종 작성
      2service_role key를 프론트엔드에 사용 DB 마스터 권한이 그대로 노출 서버 코드에서만 사용, 유출 시 즉시 재발급
      3API 키를 코드에 하드코딩 후 GitHub 푸시 봇이 공개 저장소를 스캔해 수 분 내 악용 .env 분리 + .gitignore 등록
      4select * + limit 없음 데이터가 늘면 응답이 급격히 느려지고 무료 한도 소진 필요한 컬럼만, 페이지네이션 필수
      5인덱스 없이 조건 검색 풀 스캔으로 읽은 행 수 폭증 where·join에 쓰는 컬럼에 인덱스 생성
      6await 누락 데이터 대신 Promise가 들어와 undefined 오류 DB·fetch 호출 앞에 await 확인
      7이미지를 Base64로 DB에 저장 용량과 egress가 폭증 스토리지에 업로드하고 DB에는 URL만 저장
      8error 값을 확인하지 않음 Supabase는 실패해도 예외를 던지지 않아 조용히 실패 const { data, error } = ... 후 error 반드시 체크
      9클라이언트에서만 유효성 검사 API를 직접 호출하면 우회 가능 DB 제약조건·RLS로 서버 측에서도 검증
      10브라우저 저장소를 최종 저장소로 사용 기기 변경·캐시 삭제 시 데이터 소실(Eviction) 중요한 데이터는 반드시 서버 DB에 이중 저장
