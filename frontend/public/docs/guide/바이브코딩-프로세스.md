# 바이브 코딩 개발 과정 기록 — StockMind는 어떻게 만들어졌나

> **작성일**: 2026-07-12 · **범위**: 2026-05-31(첫 커밋) ~ 2026-07-12, Phase 1~6 전 기간
>
> "바이브 코딩(vibe coding)" — 사용자가 방향과 요구를 자연어로 말하면 AI가 설계·구현·검증·문서화를
> 수행하는 개발 방식 — 으로 StockMind를 6주간 만들면서 정착된 **과정, 규칙, 효율화 장치, 교훈**을
> 기록한다. 목적은 두 가지: ① 같은 방식으로 다음 기능을 만들 때 이 문서만 보면 되도록,
> ② 어디서 시간이 새고 어디서 벌었는지를 남겨 과정 자체를 계속 최적화하도록.

---

## 1. 무엇을 어떤 순서로 만들었나 (요약 타임라인)

상세한 항목별 기록은 [DEVLOG](../DEVLOG.md)가 원본이다. 여기서는 흐름만 본다.

| Phase | 기간 | 핵심 산출물 | 바이브 코딩 관점 특징 |
|---|---|---|---|
| 1 | 05-31 | 대시보드 골격, Gemini 분석, Signal, 워치리스트 | 하루 만에 동작하는 첫 버전 — "완벽한 설계"보다 돌아가는 뼈대 먼저 |
| 2 | 06-01~02 | 지식 허브, US 리포트, 인텔 캘린더 | 기획 문서(PRD)를 먼저 쓰게 하고 그걸 스펙으로 구현 |
| 3 | 06-16~19 | KIS 실계좌 연동, 아침 브리핑, FinanceHub, 목표가 알림 | 외부 API 연동부터 실사용 데이터가 들어오기 시작 |
| 4 | 06-22~27 | 옥션허브, 자동매매, ETF, 키움 연동 | 허브(멀티 앱) 구조로 확장, 라우트 그룹 재편 |
| 5 | 07-11 | 문서 허브 발행, 매매습관 트래커, NXT 체결 복구 | **엑셀로 하던 개인 워크플로를 앱으로 이식** + 데이터 정합성 집중 점검 |
| 6 | 07-12 | 종목그룹 자동구성, ETF 패널, 노후생활 섹션, 전반 점검 | **사용자 작성 문서(sector.md, retire_PRD.md)가 곧 스펙** — 문서 → 기능 자동화 |

6주간의 궤적을 한 줄로 요약하면: **골격 → 외부 연동(실데이터) → 개인 워크플로 이식 → 문서 기반
기능 생성 → 품질 점검의 루프**다.

## 2. 협업 구조 — 역할 분담이 효율의 절반

- **사용자(제품 오너 + 유일한 실사용자)**: 무엇이 필요한지, 어떤 판단 기준(엑셀 매매습관, 섹터
  분류, 은퇴 계획)을 갖고 있는지를 자연어나 **직접 쓴 문서**로 전달. 실사용 중 이상 징후(체결
  누락, 알림 중복)를 발견해 보고. 비용이 걸린 결정(AI 모델 결제, 백필 여부)을 결정.
- **AI**: 기존 코드 패턴 탐색 → 설계 → 구현 → **실데이터로 검증** → 버전·문서 갱신 → 발행까지
  일괄 수행. 세션이 끊겨도 메모리와 transcript로 맥락을 복원해 이어서 진행.

이 분담에서 중요한 건 **사용자가 코드를 몰라도 되지만, 도메인 판단은 사용자만 할 수 있다**는 것.
SK스퀘어 종목코드 오류(문서에 016360으로 적혀 있었으나 실제는 402340)처럼 AI가 검증으로 잡는
것도 있지만, "백필에 돈을 쓸 것인가" 같은 결정은 반드시 사용자에게 돌아갔다.

## 3. 정착된 워크플로 — 기능 하나가 만들어지는 표준 경로

```
요청/문서 → ①탐색 → ②(대규모면) 계획 → ③구현 → ④실데이터 검증 → ⑤기록 → ⑥발행
```

1. **탐색**: 새 코드를 쓰기 전에 기존 패턴부터 찾는다. 예: 노후생활 기능은 새 테이블 없이
   기존 `FinanceJsonStore`(JSON 저장소)와 `analyze_json_prompt`(AI 호출) 패턴을 재사용했다.
   기존 인프라 재사용이 검토의 기본값 — "관련 ETF 패널"도 고정 목록 대신 이미 있던
   종목→ETF 역인덱스를 활용해 유지보수 비용을 0으로 만들었다.
2. **계획**: 새 허브 섹션 + 백엔드 서비스 + 스케줄러 + 프론트처럼 여러 층을 건드리면 구현 전에
   계획을 세우고 확인한다. 소규모 수정은 바로 구현.
3. **구현**: 백엔드 → API → 프론트 순서. 파일별 컨벤션(라우터 등록 방식, 카드 컴포넌트 스타일,
   api.ts 래퍼 패턴)을 그대로 따른다.
4. **실데이터 검증**: 목·mock이 아니라 **실제 DB·실제 API·실제 브라우저**로 확인한다.
   타입체크(tsc) → 백엔드 모듈 임포트 → API 실호출 → 브라우저 렌더링 확인 순.
   외부 데이터(종목코드 등)는 등록 전에 사전 검증(pykrx 이름 조회)한다.
5. **기록**: 아래 4장의 규칙에 따라 버전·changelog·DEVLOG·STATUS를 갱신한다.
6. **발행**: `./publish-docs.sh` 한 번으로 GitHub Pages + 앱 내 참고자료 동시 갱신.

## 4. 효율을 만든 장치들 (규칙과 도구)

이 프로젝트의 속도는 코드 생성 속도가 아니라 **반복 작업을 규칙으로 만들어 생략 없이 자동
수행되게 한 것**에서 나왔다. 규칙 전문은 [바이브 코딩 허브](../vibecoding.html)에 모아 두었다.

| 장치 | 내용 | 왜 효율적인가 |
|---|---|---|
| **버전 뱃지 + 변경로그** | 기능 추가 시마다 `APP_VERSION`(날짜+시간) 갱신 + `changelog.ts`에 항목 추가, 헤더 뱃지 클릭으로 열람 | 사용자가 "지금 화면이 최신인가"를 즉시 확인 — 새로고침 논쟁 소멸 |
| **DEVLOG (append-only)** | 기능·연동마다 이력 추가, 과거 항목 불변, API 키 값 절대 미기록 | 시점 기록물이라 "언제 왜 이렇게 했나"를 나중에 복원 가능 |
| **STATUS (현재 스냅샷)** | 완료/진행 중/알려진 이슈만 유지, 이력은 git·DEVLOG에 위임 | 새 세션의 AI가 이 한 장으로 현재 상태 파악 |
| **IDEAS 백로그** | 떠오른 아이디어를 한 줄로 적는 대기열, 착수 시 STATUS로 승격 | 대화 중 "그건 나중에"가 유실되지 않음 |
| **문서 형식 규칙** | 모든 문서에 날짜 표기, 리포트는 `doc/report/YYYY-MM-DD-주제.md` | 어느 시점 기준 정보인지 항상 명확 |
| **AI 메모리** | 세션 간 지속되는 규칙·주의사항 저장소 (예: "실사용 DB라 테이블 통삭제 금지", "core 함수는 내부 commit이라 rollback으로 안 지워짐") | 세션이 바뀌어도 같은 실수를 반복하지 않음 |
| **publish-docs.sh** | 문서 발행 + 앱 내 복사본 동기화 + 사설 IP 마스킹 검사를 원커맨드로 | 발행 절차가 사람 기억에 의존하지 않음 |
| **정기 전반 점검** | 다관점 병렬 코드 점검 → 건별 검증 → 수정 → 날짜 리포트 발행 | 빠르게 쌓인 코드의 품질 부채를 주기적으로 상환 (첫 회: 21건 발견, 15건 수정) |

## 5. 세션이 끊겨도 이어지는 법 — 컨텍스트 복원

바이브 코딩의 약점은 대화가 끊기면 맥락이 사라진다는 것. 이 프로젝트에서 실제로 작동한 복원 경로:

1. **메모리 인덱스** — 프로젝트 규칙·진행 중 작업·주의사항이 요약돼 있어 새 세션이 먼저 읽는다.
2. **STATUS.md** — "지금 어디까지 왔나"의 공식 스냅샷.
3. **직전 세션 transcript** — "아까 하던 작업 다시 해줘" 한 마디로, 직전 세션의 마지막 요청·중단
   지점(예: 노후생활 기능 계획 중 중단)을 찾아 그대로 재개했다. 실제로 2026-07-12 노후생활
   기능은 이 방식으로 중단 지점부터 이어서 완성됐다.

→ **사용자는 맥락을 다시 설명할 필요가 없다.** 이것이 기록 규칙(4장)에 투자한 비용의 회수처다.

## 6. 함정과 교훈 — 실제로 겪은 버그에서 뽑은 원칙

전부 이 저장소에서 실제로 발생·수정된 사례다 (상세: [DEVLOG](../DEVLOG.md), [점검 리포트](../report/2026-07-12-전반점검.md)).

1. **조용한 폴백 금지** — 장마감 스냅샷이 데이터가 없으면 몰래 전일 데이터로 대체해 이중
   저장 사고 발생. 데이터가 없으면 없다고 남기고 건너뛰는 게 낫다.
2. **외부 API의 "기본값"을 믿지 말 것** — KIS 체결조회가 파라미터 하나(`EXCG_ID_DVSN_CD`)를
   안 보내면 KRX 체결만 반환해 넥스트레이드 체결 344건이 조용히 누락됐다. 신설 파라미터가
   생기면 기존 연동을 재점검해야 한다.
3. **AI 프롬프트의 생략 표기는 스키마 붕괴를 부른다** — 프롬프트 예시를 `"topics":[...]`처럼
   줄여 쓰자 AI가 해당 필드를 아예 빼고 반환, 5주간 매크로 Signal 0건. 프롬프트의 JSON 예시는
   실제 스키마 전체를 써야 한다.
4. **falsy-zero** — "값이 0"과 "값이 없음"을 `or`/truthy로 구분하면 실측 수입 0원이 등록값으로
   둔갑한다. `is None`/`months_counted`로 명시 구분.
5. **시간대는 KST로 통일해서 생각** — 로컬 자정으로 파싱한 날짜를 `toISOString()`(UTC)으로
   포맷하면 KST에선 하루 밀린다. 날짜 문자열은 로컬 연·월·일로 직접 조립.
6. **파일 이동은 하드코딩 경로 전수 검색과 한 몸** — chart.md를 doc/로 옮기자 공부하기 레슨
   본문이 통째로 공백이 됐고, lru_cache가 빈 결과를 고정해 재시작 전까지 복구도 안 됐다.
7. **알림·저장은 엣지 트리거로** — 상태가 유지되는 동안 매 갱신마다 알림이 쌓인다(하루 8건
   중복 사례). "임계값을 처음 넘을 때 1회" 플래그 패턴을 표준으로.
8. **실사용 DB 위에서 작업 중임을 잊지 말 것** — 사용자가 대화 도중에도 앱에 실데이터를 넣는다.
   테이블 통삭제 금지, 테스트 스크립트의 commit 여부 확인은 메모리에 박아둔 상시 규칙.
9. **라이브러리가 못 따라오면 앱 쪽에서 관대하게 패치** — python-kis가 NXT 거래소코드를 몰라
   KeyError를 내던 것을 "미지 코드는 KRX로 처리"로 우회. 업스트림 수정을 기다리지 않는다.
10. **비용이 걸린 재작업은 사용자 결정** — 5주치 감성 데이터 백필은 재분석 비용 때문에 하지
    않기로 사용자가 결정. AI가 임의로 돈 드는 작업을 하지 않는 것도 규칙이다.

## 7. 다음 최적화 후보

  분석 배치 쿼리 정리, market_calendar 공휴일 지원 등).
